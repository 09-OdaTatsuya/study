Salesforce試験の要素

過去問分析で挙げた要素の意味を、なぜそれが存在するのかから解説したもの。対応表だけを暗記すると問題文の言い回しが変わった瞬間に外すため、制約の出どころを先に置いている。
§0 を読んでから、あとは引きたいところだけ引く。§0 を飛ばすと以降が全部暗記になる。

目次

    § 0大前提：制約はすべて「相席」から来る

    ここを押さえると、以降の制約を個別に暗記しなくても選択肢が自分で切れる。

    Salesforceは1台のサーバーを多数の会社が同時に使う（マルチテナント）。自社専用のサーバーではなく、知らない会社と同じ建物の同じフロアに相席している状態。

    ここから、試験に出るほぼ全ての制約が導かれる。

    • 誰か1社の重い処理で全社が止まるので、1回の処理で使える量に上限を置く（→ ガバナ制限）
    • 他社のデータが見えてはいけないので、データの見え方を厳格に制御する（→ 共有モデル）
    • 他社の都合でサーバーを止められないので、バージョンアップは全社一斉・強制（→ リリースサイクル）
    判断の型

    迷ったら「相席している建物で、これは迷惑か？」を考える。迷惑な選択肢はたいてい不正解。

    § 1ガバナ制限

    ガバナ制限Governor Limits

    1回の処理で使える資源の上限。超えると処理が強制中断されエラーになる。「ガバナ」は調速機（エンジンの回転を上げすぎないようにする部品）の意味。

    覚える主な上限（1回の処理あたり）：

    何の上限か数
    データの保存・更新・削除の命令回数（DML）150
    データの検索の命令回数（SOQL）100
    検索で取得できる件数の合計50,000
    保存・更新できる件数の合計10,000
    非同期処理（future）の呼び出し回数50
    ここが核心

    「回数」と「件数」は別の上限。1回の命令で1万件を保存するのはOKだが、1件ずつ1万回保存するのはアウト（150回で止まる）。この区別が試験の核心。

    DMLData Manipulation Language

    データを書き換える命令のこと。insert（追加）／update（更新）／delete（削除）／upsert（あれば更新・なければ追加）。

    SOQL（ソークル）Salesforce Object Query Language

    データを読む命令のこと。SQLのSalesforce版。

    SOSL（ソッスル）Salesforce Object Search Language

    複数の種類のデータを横断して全文検索する命令。SOQLが「取引先テーブルから条件で絞る」なら、SOSLは「全部から『田中』を含むものを探す」。使い分けが問われる。

    § 2バルク化

    PD1で最も出題される概念。これだけで複数問取れる。

    バルク化Bulkification

    「1件ずつ処理する」書き方をやめて「まとめて処理する」書き方にすること。必要な理由は §1 のとおり命令の回数に上限があるため。

    【悪い例】100件のループの中で、1件ずつ保存命令を出す → 保存命令 100回 【良い例】100件を箱に溜めて、ループを抜けてから 1回だけ保存命令を出す → 保存命令 1回
    合格の型

    ループの中にデータの読み書き命令を書かない。ループの外で1回だけ呼ぶ。

    選択肢の見分け方：コードが出てくる問題で、for（繰り返し）の中括弧の内側に insert / update / [SELECT ...] が書かれていたら、その選択肢は不正解。

    § 3トリガーとテスト

    トリガー

    トリガーApex Trigger

    「レコードが保存されたら自動で動く処理」。引き金の意味。

    before トリガー

    データが保存される直前に動く。この時点では値を書き換えてよい（まだ保存されていないので、書き換えてから保存される＝追加の保存命令が不要）。入力値の補正・検証はここ。

    after トリガー

    データが保存された直後に動く。関連する別のレコードを触るのはここ（自分自身を触ると再保存が必要になり非効率）。保存で初めて確定する情報（採番されたIDなど）を使えるのもこちら。

    試験での型

    自分のレコードの値を直す＝before　／　他のレコードを作る・更新する＝after

    Trigger.new ／ Trigger.old

    トリガーの中で使える「処理対象のレコードの一覧」。new＝新しい値、old＝変更前の値。「金額が変わったときだけ動かす」のように変化を検知するには両方を比べる。

    addError()

    トリガーの中からエラーを出して保存を中止させる命令。入力規則（§4）では表現できない複雑な条件で保存を止めたいときに使う。

    再帰recursion

    トリガーが自分の処理の中でまたレコードを更新し、それが再びトリガーを呼ぶ無限ループ。対策は「一度動いたら印を付けておき、2回目は何もしない」（static変数を使う）。

    テスト

    Apexテスト

    コードが正しく動くことを確認する「検査用のコード」。Salesforceでは本番環境へコードを入れる際にテストの合格が必須で、ここが他の開発環境と大きく違う。

    コードカバー率 75%

    本番へ入れるには、組織全体のApexコードの75%以上がテストで通過していることが必要。さらに全てのトリガーが最低1行はテストで通ること。

    テストはデータを見ない

    テストコードは原則、組織の実データを参照できない（@isTest(SeeAllData=true) を付けない限り）。テスト用のデータはテストの中で自分で作る。これが「テストデータを作る処理が必要」という選択肢の根拠。

    Test.startTest() ／ stopTest()

    この2つで囲んだ範囲だけ、ガバナ制限のカウントが新品に戻る。「準備のための処理で制限を使い切ってしまう」のを避けるための仕組み。

    HttpCalloutMock

    テスト中は外部システムへ通信できない（相席している建物から勝手に外へ電話をかけられない）。そのため「外部がこう返事したことにする」偽の返答を用意する仕組み。外部連携のコードをテストする問題の答えはほぼこれ。

    System.runAs()

    「別のユーザーになったつもりで」テストを動かす命令。権限や共有の設定が正しいかを検査するときに使う。

    § 4コードを書かない選択肢（宣言的機能）

    Salesforceの設計原則は「宣言的機能で済むならコードを書かない」。コードはテストと保守が必要になり、バージョンアップで壊れるリスクも負うため。

    試験での意味

    「これを実現する最適な方法は？」と問われたら、コードを使わない選択肢が正解の可能性が高い。逆に「宣言的機能では不可能」と判断させるための条件（複雑な分岐、外部通信、大量件数の処理）が問題文に埋まっていることもある。

    数式項目Formula Field

    他の項目から計算して表示するだけの項目。データとして保存されない（＝常に最新だが、検索条件に使うと重い）。

    積み上げ集計項目Roll-Up Summary

    子レコードの合計・件数・最大・最小を親に表示する項目。主従関係（master-detail）がある場合のみ使える。

    入力規則Validation Rule

    「この条件を満たさなければ保存させない」というルール。単純な条件はこれ、複雑なものは §3 の addError()。

    レコードトリガーフローRecord-Triggered Flow

    保存時に動く自動処理を、画面上の設定で組み立てる機能。かつてのワークフロールール／プロセスビルダーの後継で、現在はこれが標準。過去問に「ワークフロールール」「プロセスビルダー」が出てきたら古い（→ §13）。

    クイックアクション

    画面上のボタンから特定の操作（レコード作成、項目更新）を呼び出す仕組み。

    カスタムメタデータ型／カスタム設定Custom Metadata Type / Settings

    「設定値をコードの中に書かない」ための置き場所。しきい値や税率のような後で変わる数値をコードから追い出すのに使う。カスタムメタデータ型はデプロイで運べる点が重要（カスタム設定のデータは運べない）。

    § 5画面の作り方

    画面技術は3世代ある。新しい順に LWC → Aura → Visualforce。「どれを選ぶべきか」と「それぞれの作法」が出る。

    LWCLightning Web Components

    現行の標準。新規開発はこれを選ぶ。

    • @wire — サーバーからデータを取ってきて画面に自動で反映させる仕組み。データが変わると自動で再表示される。
    • @AuraEnabled(cacheable=true) — サーバー側の処理に付ける印。「結果を使い回してよい（＝読むだけで何も書き換えない）」という宣言。@wire で呼ぶ処理にはこれが必須。逆に、データを書き換える処理には付けられない。
    • カスタムイベント — 部品どうしの連絡手段。子から親へは「イベントを投げる」、親から子へは「直接呼ぶ」という向きの違いが問われる。
    Aura Components

    一世代前。既存のものを保守する文脈で出る。イベントを投げる命令が fire()。

    Visualforce

    最も古い世代。ただし今でも現役の用途が2つあるので捨てられない。

    • PDF出力 — renderAs="pdf" を付けると画面をPDFとして出力できる。帳票・請求書の出力を問う問題の答えはこれ（LWCには同等の標準機能がない）。
    • apex:pageMessages — エラーメッセージを画面に表示する部品。
    • StandardSetController — 一覧のページ送り（ページネーション）を担う部品。「大量の一覧を分割表示する」問題で出る。

    § 6開発と配布

    組織Org

    Salesforceの1契約単位。「本番組織」「サンドボックス」など。

    サンドボックスSandbox

    本番のコピーで作る練習・検証用の組織。種類でデータがどこまで入るかと作り直せる頻度が違う。

    • Developer / Developer Pro＝設定だけコピー（データは入らない、容量小）
    • Partial Copy＝設定＋データの一部（抽出条件を指定）
    • Full＝本番の完全なコピー。本番相当の性能検証・大量データの検証はこれしかない。作り直せるのは29日に1回。
    Dev Hub ／ スクラッチ組織Scratch Org

    「使い捨ての開発用組織」を必要なときに作って、終わったら捨てる仕組み。Dev Hub はその発行元。ソース駆動開発（設定をファイルとしてGitで管理する考え方）の中核。

    Salesforce CLI（sf コマンド）

    コマンドで組織を操作・デプロイするための道具。

    メタデータAPI／デプロイ

    設定（オブジェクト、項目、画面、コード）を組織間で運ぶ仕組み。「その設定はデプロイで運べるか」という問いが両試験に出る。

    • パスアシスタント（商談の進め方を画面に表示する機能）は運べる。
    • リストビューは運べるがワイルドカード（まとめ指定）が効かないため1つずつ列挙が必要で、さらに非公開のリストビューは運べない。
    変更セットChange Set

    画面操作で設定を運ぶ、古いが今も使われる方法。削除を運べないなどの制約がある。

    § 7データの出し入れ（API群）

    Data Architect の主戦場。「何件を、どれくらいの速さで、どういう形で入れるか」で道具が変わる。

    道具の選び方

    状況使うもの
    大量（数万件以上）をまとめて入れる・出すBulk API
    少量をその都度・リアルタイムにREST API（軽量・現代的）／SOAP API（古いが機能が厚い）
    「データが変わったら知らせてほしい」Streaming API ／ 変更データキャプチャ（§9）
    設定そのものを運ぶメタデータAPI（§6）
    Bulk API

    大量データ専用の入り口。普通のAPIが「窓口に1人ずつ並ぶ」なら、Bulk APIは「トラックで荷物を持ち込んで、裏で順次処理してもらう」方式。データをまとめてアップロードし、Salesforce側が非同期（裏側で時間をかけて）処理し、終わったら結果を取りに行く。現行は Bulk API 2.0。

    Data Loader

    Bulk API を画面から使えるようにした無料ツール。実務ではこれを使う。

    直列モードと並列モード

    Bulk API は持ち込まれたデータを細かい束（バッチ）に分けて処理する。その束を同時に処理するか、順番に処理するかの選択。

    並列モードparallel

    複数の束を同時に処理する。速い。既定（デフォルト）はこちら。

    直列モードserial

    束を1つずつ順番に処理する。遅いが、ロック競合が起きない。

    速さ優先 → 並列（既定のまま） ロック競合でエラー → 直列に切り替える

    ロック競合

    ロック

    あるレコードを書き換えている間、他の処理がそれを触れないように一時的に鍵をかけること。鍵をかけないと、2つの処理が同時に書き換えて片方が消える。

    ロック競合UNABLE_TO_LOCK_ROW

    その鍵を取り合って、待たされた側が失敗すること。エラーの文面は UNABLE_TO_LOCK_ROW。過去問にこの文字列が出たら、ほぼこの話。

    なぜ大量ロードで起きるか：子レコードを保存すると、Salesforceは親レコードにも鍵をかける（親の集計値などを整合させる必要があるため）。

    取引先A ← 商談1、商談2、商談3 …（同じ親を持つ子） 並列モードで商談1と商談2が同時に処理されると、 両方が「取引先A」に鍵をかけようとして衝突する

    対策は2つあり、両方が正解の選択肢になりうる。

    • 直列モードにする — 同時に処理しないので衝突しない。確実だが遅い。
    • 子レコードを親IDでソートしてから入れる — 同じ親を持つ子が同じ束にまとまるため、束どうしが別の親を触ることになり衝突しない。速さを保ったまま解決できるので、こちらのほうが上等な答え。
    試験での型

    「大量ロードで UNABLE_TO_LOCK_ROW が出る。速度は維持したい」→ 親IDでソート
    「確実に通したい・多少遅くてよい」→ 直列モード

    その他

    PK Chunking

    数千万件のような巨大なデータを取り出すときの技法。PK＝Primary Key（レコードID）。巨大なテーブルに「全部ください」と頼むと時間切れになるので、IDの範囲で区切って「1〜10万番まで」「10万1〜20万番まで」と小分けに取り出す。Bulk API に指示するだけで自動的にやってくれる。

    試験での型：「数千万件のオブジェクトから抽出したいがタイムアウトする」→ PK Chunking。

    外部IDExternal ID

    「他システムでの番号」を入れておく専用の項目。

    Upsert

    「あれば更新、なければ新規作成」という保存命令。外部IDを鍵にして upsert するのが、他システムとデータを同期する標準の型。Salesforce側のIDを相手に教えずに済むのが利点。連携の問題で最頻出。

    ステージングデータベースstaging database

    Salesforceに入れる前に、データを一旦置いて加工・名寄せ・検証する外部の置き場。「汚いデータをそのまま入れない」ための場所。移行の問題で「どこで重複排除・変換をするか」と問われたらこれ。

    ETL

    Extract（抽出）・Transform（変換）・Load（投入）。データ移行や連携の処理の総称。専用ツール（Informatica、Talend、MuleSoft等）がある。

    § 8大量データを抱えた組織

    LDVLarge Data Volume

    大量データを抱えた組織。数百万件を超えると、普通に動いていたものが遅くなる。その対処が Data Architect の中心論点。

    スキニーテーブルSkinny Table

    よく使う項目だけを抜き出した内部的な軽量テーブル。Salesforceが裏側で作って自動的に使ってくれるので、作っても画面上は何も変わらず、ただ速くなる。自分では作れず、Salesforceのサポートに依頼する。この「依頼が必要」という点が選択肢の分かれ目になる。

    インデックス（索引）

    検索を速くするための索引。本の巻末索引と同じ。標準で索引がある項目（ID、名前、外部ID、参照関係など）と、ない項目がある。

    クエリの選択性Query Selectivity

    検索条件が「どれだけ絞り込めているか」。絞り込めている条件は索引が使われて速い。絞り込めていない条件（全体の大部分が該当する条件、!= や NOT、LIKE '%xxx' のような前方不一致）は索引が使われず遅い。

    試験での型：「クエリが遅い」→ 索引のある項目で絞る／選択性のない条件を外す。

    Big Object

    数十億件規模を保存するための特殊なオブジェクト。読み書きが限定的（通常の検索・画面・レポートがほぼ使えない）な代わりに、際限なく溜められる。用途は履歴・ログ・監査記録のアーカイブ。「過去データを消したくないが現行データを軽くしたい」という問題の答え。

    データアーカイブ

    古いデータを本体から外へ出す行為。出し先の選択肢＝Big Object ／ 外部ストレージ（§9の Salesforce Connect で読む）／ 外部のデータウェアハウス。

    共有計算の延期Defer Sharing Calculation

    大量データを入れる前に「誰が何を見られるかの再計算」を一時的に止めておき、作業後にまとめて計算させる設定。ロールや共有ルールを大量に変更するときに、これをしないと計算が延々と走って組織が重くなる。

    データのロード順序

    大量移行では親→子の順に入れる（親がいないと子を紐付けられない）。あわせて、ロード中はトリガー・入力規則・ワークフロー・共有計算を一時的に止めるのが定石（止めないと1件ごとに余計な処理が走る）。

    § 9外部システムとの連携

    判断の分かれ目は「データをSalesforceにコピーするか、相手に置いたまま見るか」。これが連携の問題の主軸。

    Salesforce Connect旧 Lightning Connect

    データをコピーせず、外部システムに置いたまま、Salesforceの画面で見る仕組み。見るたびに相手へ問い合わせる。

    • 外部オブジェクト — その「外部に実体があるデータ」をSalesforce上で表す器。見た目は普通のオブジェクトだが、中身は相手のもの。検索・レポート・トリガーなど使えない機能がある。
    • OData — 外部オブジェクトが外部システムと話すときの標準的な通信規格。相手がこれに対応していればつなぐだけで済む。
    • Apexコネクタフレームワーク — 相手が OData に対応していない場合に、つなぎ方を自分でコードで書くための仕組み。

    試験での型：「大量の履歴データがあるが、Salesforceのストレージを消費したくない／コピーを持ちたくない」→ Salesforce Connect ＋ 外部オブジェクト。

    マッシュアップMashup

    外部システムの画面をそのままSalesforceの画面の中に埋め込んで見せる方式。データも画面も相手のまま。最も軽いが、Salesforce側では一切扱えない。

    Salesforce to SalesforceS2S

    Salesforce組織どうしでレコードを共有する専用機能。「取引先を別組織と共有したい」という問題で出る。

    変更データキャプチャChange Data Capture / CDC

    Salesforce側でデータが変わったときに、変更内容を外部へ通知する仕組み。外部が「変わったか？」と定期的に聞きに来る（ポーリング）のをやめさせられる。

    Platform Events

    「出来事」を発信して、受け取った側が各自処理する連携方式。送り手と受け手を切り離せる。

    MDMMaster Data Management

    「どのシステムの値を正とするか」を決めて管理する考え方・仕組み。複数システムに同じ顧客がいるときの正本の決め方。システム・オブ・レコード（SOR）＝その項目の正本を持つシステム。設計の問題で「どちらを正とするか」を問われたらこの概念。

    データウェアハウス

    分析のために複数システムのデータを集める置き場。Salesforceの外。

    § 10データモデルの落とし穴（スキュー）

    データスキューData Skew

    データの偏り。1つのレコードに子が偏って集まると、§7で説明したロックの取り合いが起きて性能が落ちる。目安は1万件。

    3種類あり、区別が問われる。

    所有権スキューOwnership Skew

    1人のユーザーが1万件以上のレコードを所有している状態。よくある原因は「移行時に全部を管理者が所有した」「取りこぼし用のダミーユーザーに寄せた」。所有者の変更やロールの移動のたびに、共有の再計算が大量に走る。

    対策：所有者を分散させる。やむを得ない場合、そのユーザーをロール階層に入れない（階層に入れると上位への再計算が連鎖する）。

    主従関係のスキューMaster-Detail Skew

    1つの親に子が1万件以上。子を保存するたびに親に鍵がかかるため、§7のロック競合が起きる。

    参照関係のスキューLookup Skew

    1つの参照先レコードを、大量のレコードが参照している状態。同じく保存時の競合を招く。

    対策：参照先を複数に分散させる（例：ダミーの「未割当」レコードを1つではなく複数用意して振り分ける）。

    暗黙的な共有Implicit Sharing

    Salesforceが自動的にかける共有。例：商談を見られる人は、その親の取引先も（読み取りだけ）見られる。設定していないのに見えてしまう／見えてしまわないのはこれが理由。消せない。

    個人取引先Person Accounts

    「取引先（会社）」と「取引先責任者（人）」を1つにまとめた、個人顧客（B2C）向けの形。一度有効にすると戻せない。有効化すると件数や共有の扱いが変わるため、設計の問題で「B2Cを扱うには」と問われたらこれ。影響の大きさとあわせて覚える。

    § 11セキュリティと共有

    誰が何を見られるか（4層）

    • オブジェクトレベル — 「商談というデータの種類そのものを触れるか」（プロファイル／権限セット）
    • 項目レベル — 「商談の中の『原価』という項目を見られるか」（項目レベルセキュリティ）
    • レコードレベル — 「その商談のうち、どのレコードを見られるか」（組織の共有設定＋ロール階層＋共有ルール＋手動共有）
    • 画面・項目の出し方 — ページレイアウトなど。これはセキュリティではない。隠しただけでAPIからは見える。試験の引っかけ
    プロファイル／権限セット

    権限の束。現在の推奨は「プロファイルは最小にして、権限セットで足していく」（権限セットは複数重ねられるため、人ごとの例外に対応しやすい）。

    組織の共有設定OWD

    「既定では他人のレコードを見られるか」の土台。非公開／参照のみ／参照・更新。土台を厳しくして、必要な人にだけ開けていくのが原則。

    ロール階層／共有ルール

    ロール階層＝上司は部下のレコードを見られる、という縦の広げ方。共有ルール＝条件や所有者のグループを指定して横に広げる設定。

    コードの中でのセキュリティ

    重要な前提

    Apexコードは既定で権限を無視する（システム権限で動く）。つまり「画面では見えない項目も、コードからは読めてしまう」。だから明示的に守る必要がある。これがPD1の出題ポイント。

    with sharing ／ without sharing ／ inherited sharing

    with sharing＝レコードの共有設定を守る。without sharing＝無視する（既定の挙動）。inherited sharing＝呼び出し元に従う。最も安全な既定として推奨される書き方。

    WITH SECURITY_ENFORCED

    検索命令（SOQL）に付けると、見る権限のない項目が含まれていたらエラーにする。全か無かの挙動。

    Security.stripInaccessible()

    見る権限のない項目を、結果から黙って取り除く。エラーにせず処理を続けられるので、実務ではこちらが使いやすい。

    試験での型

    「権限のない項目を除外して処理を続けたい」→ stripInaccessible
    「権限がなければ止めたい」→ WITH SECURITY_ENFORCED

    暗号化

    Shield プラットフォーム暗号化

    保存されているデータを暗号化する有償機能。暗号化すると、その項目は検索・並び替え・一部の機能で使えなくなるという代償がある。「暗号化すれば万事解決」という選択肢は不正解になりやすい。

    クラシック暗号化

    古い方式。専用の項目型を使い、文字数制限がある。

    § 12監査・保持・分類

    項目履歴管理Field History Tracking

    「誰がいつ何をどう変えたか」を項目単位で記録する機能。保持期間は標準で18〜24か月。追跡できる項目数にも上限がある。

    Field Audit Trail

    上記を最長10年まで保持できるようにする有償機能。「規制で長期保存が必要」という問題の答え。

    設定変更履歴Setup Audit Trail

    設定を誰がいつ変えたかの記録。標準では6か月分。

    イベントモニタリングEvent Monitoring

    「誰がどのデータをダウンロードしたか」「誰がどのレポートを見たか」といった利用のログを取る有償機能。データの中身の変更履歴ではなく、行動の記録。この区別が問われる。

    データ分類Data Classification

    項目に「機密度」「個人情報か」などのラベルを付けておく機能。実際のアクセス制御はしない（ラベルを付けるだけ）。棚卸し・説明責任のための機能。

    同意管理Authorization Form Consent

    「本人がどの利用に同意したか」を記録する標準の仕組み。GDPR等への対応で出る。

    Data Mask

    サンドボックスにコピーされた本番データを、匿名化・置換する無償ツール。「開発者に本番の個人情報を見せたくない」問題の答え。

    バックアップ

    Salesforceの標準機能（週次エクスポート、レポート）では復元ができない（データは取れるが、関連を保ったまま戻す手段がない）点が重要。復元を含むなら Salesforce Backup か AppExchange の製品、または外部のバックアップ基盤が必要。
